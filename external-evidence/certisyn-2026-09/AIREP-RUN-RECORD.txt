## Implementation

Python 3, standard library only, no third-party dependencies.
RFC 8785 JCS and RFC 8032 Ed25519 verification written from the RFCs.
Ed25519 checked against RFC 8032 section 7.1 vectors, JCS against RFC 8785
Appendix B, before either was used on corpus material.

## CLS-LEX1 — the case predicted to disagree

Agrees. The checker reads the source lexeme of the witness claim's numeric
members rather than the decoded value, so `"length": 1e0` is caught by the E-1
rule and the case yields witness-claim-invalid.

Proven in both directions rather than asserted:
  * spelling that member `1` instead of `1e0` turns the same case into
    AIREP-Witnessed with all five channels empty, so the lexical form is the only
    defect present;
  * injecting `1e0` into the clean CLS-P2 case makes that case fail the same way.

There is therefore no reconstruction-path finding on this row.

## The one disagreement — CLS-XT1

Frozen fields agree exactly: class AIREP-Core, all five reason channels,
observer assessment, process exit, run validity, and signing input
reconstruction. The disagreement is confined to `cryptographic_result`, which is
a package-derived projection rather than a frozen field.

    expected   PASS
    observed   NOT_EVALUATED

XT1 is a revoked producer binding with a clean witness. Contract section 4 and
ruling R-6 make stage 4's prerequisite "binding accepted and not definitively
revoked", so on a revoked binding the signature gate does not run and no
signature is verified under any key. The projection rule recorded in METHOD.md
branches on a signature reason (FAIL) and on a withheld binding (NOT_EVALUATED),
and a revoked binding is neither, so it falls through to PASS.

Reporting PASS on that row states that a cryptographic check succeeded when no
cryptographic check executed. The frozen fields are not in dispute and were not
touched. METHOD.md invites disputing the projection rather than the frozen
fields, and this row does that.

## Coverage observations on the corpus

Two input classes are not exercised by the 18 cases. Both were found by mutation
testing this implementation rather than by any corpus case, and both are recorded
here because they are facts about the corpus's reach:

  1. No case carries a JSON number whose shortest representation uses exponential
     notation with a fractional mantissa (magnitude at or above 1e21, or below
     1e-6). Every number in the corpus is 0, 1, 2 or 3600. RFC 8785 number
     serialisation is therefore required by CAPABILITY_REQUIREMENTS.md but only
     partially exercised.
  2. No case carries a timestamp before 1970. common.schema.json permits years
     from 0000, and the freshness predicate is arithmetic on those values, so the
     pre-epoch path is reachable but unmeasured.

Neither observation changes any result above.
